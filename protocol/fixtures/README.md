# Protocol Fixtures

Home for canonical JSON, expected digests, signing inputs, verification outputs, and generated binding drift fixtures.

All fixture content in this public/open area must be synthetic or public non-customer content only. Any Raw Snippet-like example must be clearly labeled `SYNTHETIC_DEMO_DATA` and `NOT_CUSTOMER_SOURCE`.

Story 1.3 owns real JSON Schema 2020-12 contracts, RFC 8785 canonicalization fixtures, signing-input fixtures, and the first authoritative canonical fixture content.

When fixture files change, update `canonical-manifest.json` with deterministic `sha256` hashes. The local drift gate uses git diff in source-control workspaces and this manifest as the direct compare/hash fallback in non-git workspaces. The manifest also records expected RFC 8785 identities for `manifest_id` and `evidence_bundle_id`.

`npm run fixtures:coverage` derives calendar-timestamp and enum-bearing schema inventories, then verifies the C1 coverage matrix documented in `protocol/docs/fixture-coverage.md`.

`protocol/fixtures/v0/fixture-index.json` maps valid and negative fixtures to schemas. Negative fixtures are intentional and prove the gate rejects camelCase fields, missing retention/source-derived class, invalid coverage mode, malformed digests, unsafe Raw Snippet metadata, and scanner output that tries to become reviewer classification. Scanner finding set fixtures also exercise file-level `scanned_files` metadata and the absence of unapproved raw scanner output artifacts.

Story 1.6 adds disclosure-policy fixtures for all three v1 coverage modes: Metadata-only, Finding-context snippets, and Extended approved snippets or targeted files. Its negative fixtures prove obsolete mode names are rejected, metadata-only cannot include snippets, finding-context snippets require caps, extended mode requires selected files or areas, retained source requires opt-in plus a retention period, redaction cannot claim proof that secrets are absent, and disclosure policy fields remain `snake_case`.

Story 1.7 expands the outbound-manifest fixture into the preview-before-send approval surface. The valid manifest fixture lists every evidence category, records preview-only package state, keeps approval at `not_requested`, exposes copyable review-scope / scanner / policy references, and computes `manifest_id` from `outbound-manifest.identity-input.json` with `manifest_id` excluded. Negative outbound-manifest fixtures prove missing or duplicate categories are rejected, manifest and policy Coverage Mode cannot drift, metadata-only mode cannot include snippets, source-code disclosure rows need visible labels and caps, redaction configuration needs limitation/version wording, malformed or self-referential manifest identities fail, camelCase fields remain invalid, and preview state cannot become approved or send-ready.

Story 1.8 adds customer approval and signed Evidence Bundle fixture chains without changing Story 1.7 preview safety. Valid approval fixtures cover approved and declined decisions; the declined fixture remains `not_submitted` and records revise-policy, rerun-scan, export-manifest, and exit actions. The valid bundle fixture references the approved decision, outbound manifest, review scope, scanner finding set, Disclosure Policy, and synthetic Raw Snippet artifact, computes `evidence_bundle_id` from `bundle-manifest.identity-input.json`, and records cleanup intent for transient source-derived artifacts. Negative Story 1.8 fixtures prove missing approval context, declined approval used for bundle construction, bundle/manifest identity mismatch, self-referential bundle identity input, missing retention/source-derived class, missing cleanup intent, signature signed identity mismatch, and camelCase fields are rejected.

Story 1.9 adds local-runner-attempt fixtures for failure, rerun, status, and runner trust states. Valid fixtures cover pre-approval failure, post-approval packaging failure with preserved approval metadata and no signed bundle, successful local rerun with distinct bundle/submission identities, declined approval, and unsigned/demo runner trust reporting. Negative fixtures prove failed pre-approval attempts cannot carry bundle identities, post-approval failures must preserve manifest/approval metadata, local status must not use Vendor Receipt or finalized wording, unsigned/demo trust must be labeled, diagnostics must not leak raw source text, and fields remain `snake_case`.

Story 2.0 hardens the trust prerequisites before Epic 2 intake and receipt work. Artifact-reference fixtures now include `content_path_anchor` and the semantic gate rejects host-local absolute paths, Windows drive prefixes, backslashes, traversal, null bytes, and unanchored content paths. `environment-evidence-gate.*.json` fixtures prove synthetic demo mode rejects real source-derived evidence and that real Raw Snippet / targeted-file readiness requires all evidence-handling controls. `v0/invariants.json` records the shared JavaScript/Rust invariant coverage inventory used by the Story 2.0 prerequisite gate.

Sub-project G Task 1 adds one content-addressed `environment-readiness-evidence` fixture per readiness control, approved and declined content-addressed decisions, and a real ML-DSA-65 managed-key signature over the approved decision identity. Negative fixtures prove stale, duplicate, missing, failed, self-reviewed/self-approved, wrong-release, wrong-gate-digest, and declined-decision promotion paths fail closed. These fixtures are synthetic acceptance machinery only; they do not assert that the live pilot controls passed or authorize the environment gate to be raised.

Story 2.3 adds Vendor Receipt fixtures. `v0/valid/vendor-receipt.json` records a synthetic-demo received-with-receipt state with a canonical `vendor_receipt_id`, embedded receipt signature envelope, approved-vs-received comparison rows, explicit artifact count summaries, and public verification metadata for historical key id/version. `v0/valid/vendor-receipt.identity-input.json` excludes the self id, signature envelope, and repeated signed identity; `v0/signing-inputs/vendor-receipt-identity.json` and `v0/valid/signature-envelope.receipt.json` exercise typed receipt signing. Negative receipt fixtures prove self-reference, invalid timestamps, missing key metadata, wrong identity type/value, approved/received mismatches, and rejected/quarantined no-receipt misuse are blocked.

Story 3.2 adds `finding-classification-record.*.json` fixtures for reviewer-only expert classification. Valid fixtures cover every allowed classification (`likely`, `confirmed`, `inconclusive`, and `requires_customer_side_validation`), including confirmed submitted-evidence and confirmed scanner/metadata evidence with explicit defensible criteria. Negative fixtures prove disallowed taxonomy, missing Review Finding draft references, confirmed-without-criteria, scanner-only/metadata-only confirmed without defensible criteria, validation-required without a validation path, missing evidence basis/limitations, scanner execution or Attestation copy fields, camelCase fields, raw source-like text in rationale, and customer-authored classifications are rejected.

Review-event fixtures use `classification_recorded` as a compact append-only envelope that references a typed classification artifact through `artifact_refs`. Do not encode classification details only in free-text `reason`; the `finding-classification-record` artifact owns taxonomy, evidence basis, criteria, limitations, validation path, and rationale. Corrections append a later event with `supersedes_event_id` or a later classification record with prior-reference fields so prior history remains visible.

Epic 5 fixtures cover a section-complete claim-safe Attestation, approved SOC 2 supporting-evidence mapping, content-addressed static manifest, offline portal projection, customer-owned package finalization, real ML-DSA-65 static/finalization signature envelopes, and bounded internal pilot metric/feedback records. Negative fixtures prove acceptance claims, customer-package pilot-learning leakage, non-customer finalization, and customer-facing internal feedback fail closed. Every signature fixture is a real ML-DSA-65 signature produced by `scripts/regenerate-signature-fixtures.mjs` from the committed deterministic test seed, under `ml_dsa_65` with explicit key-custody limitations.

Runner, intake, worker, web, and static bundle code must pass these fixtures before protocol behavior changes. Do not replace the shared fixtures with package-local examples.
