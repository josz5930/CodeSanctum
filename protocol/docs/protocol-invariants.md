# Protocol Invariants

`protocol/fixtures/v0/invariants.json` is the protocol-owned inventory of cross-field invariants that must stay aligned across JavaScript protocol gates, generated bindings, Rust Local Runner behavior, and future Epic 2 intake verification.

Each invariant entry records:

- `id` — stable identifier for audits and review follow-ups.
- `artifact` — the protocol artifact or gate surface it protects.
- `summary` — the behavior that must not drift.
- `javascript_coverage` — semantic gate, fixture, or script marker that exercises the invariant.
- `rust_coverage` — Rust runner helper, validator, or test marker that exercises the same invariant.

The Story 2.0 prerequisite gate fails if an invariant lacks either JavaScript or Rust coverage markers. This does not make JSON the only implementation of the invariant; it makes the shared inventory visible before Epic 2 intake starts rejecting, quarantining, or receipt-signing evidence.

The inventory currently covers Disclosure Policy, Outbound Manifest, Artifact Reference, Customer Approval, Bundle Manifest, Signature Envelope, Local Runner Attempt, bundle artifact copy verification, Environment Evidence Gate behavior and readiness-decision proof binding, Vendor Receipt identity/signature/comparison/key-metadata behavior, and Review Event Log append/identity/supersedes/visibility behavior.

## Schema and semantic authority (C1-01)

Protocol v0 uses Draft 2020-12 conditionals for cross-field rules that can be stated without comparing two independently supplied values. The JavaScript semantic validators and applicable Rust Local Runner validators remain in place as defense in depth; moving a rule into a schema does not remove its runtime check.

The schema-authoritative inventory is grouped by artifact family:

- **Submission and receipt:** outcome state controls receipt presence, failure codes, and next path; scanner-run status controls `failure_reason`; Vendor Receipt comparison rows contain each of the seven required fields exactly once.
- **Review and classification:** review-event type controls actor authority, visibility, supersession fields, and lifecycle-class presence; classification state controls confirmation and validation-path requirements; draft normalization status controls draft/no-findings shape; draft evidence availability controls display, deletion proof, and availability flags.
- **Retention and deletion:** stored-object kind/profile restricts source-derived class; lifecycle event type requires deletion/access/retention fields; minimization category pins lifecycle class and deletion proof.
- **Environment and disclosure:** environment profile, readiness, and opt-in class form one acceptance matrix; disclosure coverage mode controls snippet policy and included raw/targeted categories; scanner inclusion requires a scanner finding-set reference.
- **Verification:** verification status controls required next steps and criterion-result states; unresolved addendum findings prevent finalization and require finding/addendum next steps.
- **Attestation and static bundle:** Attestation sections contain each required section type exactly once; finalization state controls export timestamp presence.
- **Pilot records:** content-free, PII-free, internal-only, and bounded-value requirements are direct schema constants/enums. Review-event conditionals keep pilot events internal and actor-bounded.

The schema interpreters in `scripts/lib/protocol-utils.mjs` and `packages/protocol-ts/src/validation.ts` intentionally support the conditional keyword subset used here: `allOf`, `anyOf`, `oneOf`, `not`, `if`/`then`/`else`, `contains` with `minContains`/`maxContains`, and `dependentSchemas`. The schema-parity corpus and focused mutations require both interpreters to return the same keyword-error set.

### Semantic-only rules

Standard Draft 2020-12 has no portable `$data` facility and cannot recompute hashes, resolve other artifacts, interpret prose, or compare arbitrary sibling values. The following therefore remain semantic-only and must not be weakened:

- equality and ordering between sibling fields, timestamps, versions, totals, approved/received values, or duplicated identifiers;
- RFC 8785 content-addressed identity recomputation, signature verification, digest/size verification, and canonical signing-input construction;
- cross-document reference resolution, uniqueness across documents/log history, append-only sequencing, supersession-family checks, and authoritative scope/receipt/bundle chain binding;
- count totals derived from category rows and Vendor Receipt `approved_value === received_value` comparisons;
- claim-safety, source-code/secret/PII screening, warning/limitation meaning, and other human-language requirements;
- retention chronology and deletion causality where the compared evidence timestamp lives in another artifact;
- filesystem containment, artifact-byte admission, scanner-to-file provenance, and candidate-to-shipped-artifact resolution.

## Environment readiness acceptance (Sub-project G)

- **Evidence is the authority for each boolean** (`environment-readiness-evidence-decision-gate-binding`) — each of the seven readiness controls has a separate content-addressed evidence record bound to the `pilot` deployment, exact release and deployment digests, immutable attachment digests, observation and review times, a producer, an independent reviewer, a result, and limitations.
- **Approval binds one exact proposal** — an approved decision contains each control exactly once, accepts only fresh passing evidence for its exact release/deployment, records distinct security and operations approvers who did not produce the evidence, and carries a managed-key ML-DSA-65 signature over its content-addressed identity. A declined decision is retained without a signature and may accurately bind failed evidence.
- **The gate link is non-circular** — `proposed_gate_approval_input_digest` hashes the final canonical gate body with only `readiness_decision_ref` excluded. The decision identity excludes its own id and signature; the final gate then references that identity. A different gate body, declined decision, stale record, duplicate/missing control, failed result, or release mismatch cannot validate as an approved promotion.

Server-side-only artifact families use explicit `not_applicable_*` Rust coverage markers because the Local Runner neither produces nor consumes those records. Rules at the Local Runner boundary retain corresponding Rust validation and tests; JavaScript-only coverage is not treated as a substitute there.

## Review Event Log invariants (Story 2.4)

The Review Event Log is the vendor-side system of record, so its invariants are about what an append may *not* do:

- **Append-only ordering** (`review-event-append-only-ordering`) — a newly appended event's `sequence_number` is strictly greater than every `sequence_number` already in the log, `event_id` values are unique, and no existing element is rewritten, reordered, or removed. A repeated `idempotency_key` is an append no-op rather than a second entry. JavaScript coverage: `validateReviewEventLogSemantics` in `scripts/lib/protocol-utils.mjs` and `appendReviewEvent` in `apps/control-plane/src/index.ts`.
- **Content-addressed event identity** (`review-event-content-addressed-identity`) — `event_id` equals the sha256 of the RFC 8785 canonical event content excluding `event_id`, declared on the event itself as `canonicalization: "rfc8785"`, `identity_hash_algorithm: "sha256"`, and `identity_input_excludes: ["event_id"]`. This is the same machinery as `vendor_receipt_id`, so deterministic re-serialization is checkable by `verifyCanonicalIdentity`, and a future hash chain only has to add `previous_event_id` to the canonical content. No event field names a datastore key, file path, or byte offset. JavaScript coverage: `validateReviewEventSemantics`, `verifyCanonicalIdentity`, and `computeReviewEventId`.
- **Supersedes, never rewrite** (`review-event-supersedes-not-rewrite`) — corrections are expressed only through `supersedes_event_id` pointing at an earlier event in the same log, and customer-authored events of any event type must not supersede an expert `classification_recorded` event. JavaScript coverage: `validateReviewEventLogSemantics` and `appendReviewEvent`.
- **Visibility and customer projection** (`review-event-visibility-customer-projection`) — every event declares exactly one `visibility`, `internal_note` may appear only on `internal_only` events, and the customer-facing projection omits `internal_only` events entirely (matching the shipped `TimelineEvent` primitive) while preserving `event_type`, `event_timestamp`, `actor_category`, `artifact_refs`, and `reason` when present. `internal_note` is structurally impossible in the projection because `review-event-customer-projection.schema.json` has no such property and sets `additionalProperties: false`. JavaScript coverage: `validateReviewEventSemantics`, `validateReviewEventCustomerProjectionSemantics`, `projectCustomerFacingHistory`, and `buildReviewHistoryTimeline`.

These four invariants carry `not_applicable_review_event_log_is_server_side` as their Rust marker, matching the Vendor Receipt precedent: the log is a server-side control-plane artifact that the Local Runner never produces.

Future intake code should either call the same protocol utilities where practical or mirror these invariant IDs in intake-side tests so drift is explicit during review.

## Evidence storage, access, and deletion invariants (Story 2.5)

Story 2.5 makes "evidence storage and deletion controls are explicit before real snippets are accepted" provable from artifacts rather than from status labels:

- **Single retention class per stored object** (`stored-object-single-retention-class`) — every stored object, payload, export, and log field declares exactly one retention/source-derived class. `log_or_trace`, `analytics_record`, `crash_report`, and `support_attachment` kinds may only declare `never_collected` or `retained_review_artifact`, so the surfaces most prone to accidental leakage cannot carry source-derived content even transiently. `customer_opt_in_retained_source` is only permitted under `environment_profile: partner_pilot_real_snippet_ready`. JavaScript coverage: `validateStoredObjectClassificationSemantics` in `scripts/lib/protocol-utils.mjs` and `classifyStoredObject` in `apps/control-plane/src/index.ts`.
- **Deletion is proven by Deletion Evidence** (`evidence-deletion-proven-by-deletion-evidence`) — deletion is an append-only `evidence_deleted` lifecycle event that references a `deletion-evidence` artifact and declares its `source_derived_class`. An event with no `deletion_evidence_ref` is rejected (`deletion_event_missing_deletion_evidence`), so a status label alone is never a receipt of deletion. The Deletion Evidence artifact records the deleted artifact digests, deletion method, timestamp, actor, and verification status — never the deleted bytes. JavaScript coverage: `validateEvidenceLifecycleEventSemantics` and `appendEvidenceLifecycleEvent`.
- **Access is scoped and logged** (`evidence-access-is-scoped-and-logged`) — sensitive artifact inspection appends an `evidence_accessed` event carrying actor, timestamp, artifact references, tenant/review `access_scope`, and `purpose` where available. Access outside the actor's tenant/review scope is denied and appends nothing, so no event can imply an inspection that did not occur. JavaScript coverage: `validateEvidenceLifecycleEventSemantics` and `enforceScopedAccess`.
- **Append-only lifecycle** (`evidence-lifecycle-append-only`) — an appended event's `sequence_number` is strictly greater than every one already present, `event_id` values are never reused, and no existing event is rewritten, reordered, or removed. A repeated `idempotency_key` is an append no-op; a different body under that key is a rewrite and is rejected. Unlike Story 2.4's log, identity here is a stable pattern-validated string and the discipline is in-memory only. JavaScript coverage: `appendEvidenceLifecycleEvent`.
- **Opt-in retention requires period and approval** (`retention-opt-in-requires-period-and-approval`) — a `retention-opt-in-record` requires `customer_opt_in_retained_source`, a customer approval reference, a retention period whose `end_timestamp` is after its `start_timestamp`, and the retained artifact identities; later retention-status and deletion events reference the record through `retention_record_ref`. The record carries no `environment_profile` field, so the pilot-profile gate is enforced where the profile is actually known rather than inside the record validator: `recordOptInRetention` takes the profile as a parameter, and `classifyStoredObject` enforces it per stored object. JavaScript coverage: `validateRetentionOptInRecordSemantics` (schema-required fields and period ordering), `recordOptInRetention` (profile gate), and `classifyStoredObject` (profile gate per stored object).
- **Minimization categories stay distinct** (`evidence-minimization-categories-distinct`) — `retained_finding`, `retained_metadata`, `retained_attestation`, `retained_customer_opt_in_snippet`, `deleted_transient`, and `never_collected` each pin exactly one source-derived class, one `artifact_ref` may not appear under two different categories (an artifact cannot render as both deleted and retained), and every `deleted_transient` entry resolves to a Deletion Evidence reference rather than a dangling one. Categories are not one-per-projection: a real review has many `retained_finding` entries. This is the projection *contract*; building real Signed Static Bundle or portal assets from it belongs to Epic 5. JavaScript coverage: `validateEvidenceMinimizationProjectionSemantics` and `buildEvidenceMinimizationProjection`.

These six invariants carry `not_applicable_evidence_storage_is_server_side` as their Rust marker: evidence storage, access enforcement, and deletion are vendor-side control-plane concerns that the Local Runner never performs.

Story 2.5 changes nothing about the `environment-evidence-gate` contract. Readiness booleans remain the only thing that gates real Raw Snippet acceptance, and nothing in this slice makes real snippets acceptable in a `synthetic_demo` profile.

## Submission failure and quarantine invariants (Story 2.6)

Story 2.6 makes the three intake outcomes structural rather than conventional. `submission-outcome.schema.json` is the protocol artifact for *any* submission result, and failed/quarantined attempts are recorded in the existing Story 2.4 `review-event-log` as submission events:

- **The three outcomes are mutually exclusive and complete** (`submission-outcome-states-mutually-exclusive`) — `outcome_state` is exactly one of `received_with_receipt`, `rejected_no_receipt`, or `quarantined_no_receipt`. `received_with_receipt` requires a `vendor_receipt_ref` and carries no `failure_reason_codes`; both failure states carry at least one reason code and no receipt reference at all. `next_path` may only be one the state can back (`verify_receipt` for a receipted success, `retry`/`contact_support` for a rejection, `quarantine_support`/`contact_support` for a quarantine), and failure copy is checked against the shared claim-safe forbidden-phrase list so a rejection or quarantine can never read as a review outcome. A receipt-eligible verification with no minted receipt is refused (`submission_outcome_receipt_required`) rather than downgraded into a softer success. JavaScript coverage: `validateSubmissionOutcomeSemantics` in `scripts/lib/protocol-utils.mjs` and `buildSubmissionOutcome` in `services/intake/src/index.ts`.
- **Submission failure events use the review-event-log** (`submission-failure-events-use-review-event-log`) — a rejected or quarantined outcome is recorded as `submission_rejected` / `submission_quarantined` in the existing append-only review event log. The event must reference its outcome through `artifact_refs`, derive `idempotency_key` from `(bundle_instance_id, submission_attempt_id)`, and rely on `appendReviewEvent` for distinct retry conflict handling and sequence ordering. JavaScript coverage: `validateReviewEventSemantics`, `validateSubmissionReviewEventOutcomeReferences`, `buildSubmissionOutcomeEvent`, `appendReviewEvent`, and `buildSubmissionAttemptTimeline`.

`failure_reason_codes` is a `pattern`-constrained snake_case vocabulary rather than an enum on purpose: the codes live at their throw sites in `services/intake` and are expected to grow as verification tightens. The protocol constrains *shape and presence* — at least one code on failure, none on success — and the service owns the vocabulary, so a new check is not a protocol version bump.

The protocol `next_path` vocabulary and the Story 2.1 `RiskWarningNextPathType` vocabulary stay deliberately different — the protocol records what the *system* offers, the UI records what an *audience* may act on. `packages/ui/src/submission-failure.ts` maps between them (`retry` → `retry`, `quarantine_support` → `quarantine`, `contact_support` → `support`, `verify_receipt` → `verify_receipt`) so the existing audience gating works unchanged. Because a `quarantine` path is dropped entirely for `audience: "customer"`, `projectSubmissionFailureNotice` always offers a support path alongside the outcome's own next path; without it a customer-facing quarantine notice would render with no actionable path at all.

Claim-safe copy enforcement uses the shared `@onevps/protocol-ts` phrase list in both protocol gates and control-plane runtime boundaries. The list intentionally blocks multi-word assurance claims such as `codeattest reviewed`, `review complete`, `auditor acceptance`, and `no vulnerabilities`, while allowing ordinary reviewer prose that mentions submitted/received/attestation/certified context without making an assurance claim.

Both invariants carry `not_applicable_intake_outcome_is_server_side` as their Rust marker: the intake disposition and review-event-log projection are vendor-side, and `local-runner-attempt` remains the Local Runner's pre-submission model. This story makes the failure *state* explicit; quarantine release, expiry, re-review, and operator workflow are out of scope.

## Candidate finding normalization invariants (Story 3.1)

Story 3.1 introduces `review-finding-draft-set.schema.json` as the protocol-owned artifact for reviewer-ready drafts created from scanner Candidate Findings and received evidence references. It deliberately does not classify findings, generate remediation guidance, mint receipts, create Attestation copy, execute scanners, or mutate the review-event log:

- **Receipt-gated normalization** (`review-finding-drafts-receipt-gated`) — normalization requires a known Vendor Receipt in `received_with_receipt` state and preserves the matched evidence bundle, manifest, and source scanner finding set identities. Rejected, quarantined, or no-receipt inputs are not normalizable. JavaScript coverage: `validateReviewFindingDraftSetSemantics`, `normalizeCandidateFindings`, and the worker receipt-boundary tests.
- **Scanner outputs remain inputs only** (`review-finding-drafts-inputs-only`) — drafts preserve candidate ids, scanner source, scanner rule ids, affected areas, scanner-provided severity/confidence, and evidence references as provenance. Expert-only fields such as classification, remediation guidance, validation path text, Attestation copy, receipt semantics, and scanner execution controls are forbidden in the artifact and not emitted by the worker. JavaScript coverage: `validateReviewFindingDraftSetSemantics`, `normalizeCandidateFindings`, and worker grouping/forbidden-copy tests.
- **Evidence availability and threshold gaps stay explicit** (`review-finding-drafts-evidence-availability`) — every draft records Coverage Mode, evidence basis, source reference state, and threshold gaps for scanner-only, metadata-only, deleted, not-submitted, never-collected, or unresolved evidence. Deleted-under-policy source-derived content renders as `deleted` with deletion evidence when available, never as available content. JavaScript coverage: `validateReviewFindingDraftSetSemantics`, `normalizeCandidateFindings`, and worker coverage/deletion tests.
- **No-findings copy stays claim-safe** (`review-finding-drafts-no-findings-claim-safe`) — a no-findings normalization emits no drafts, uses the exact statement `No findings were produced by the configured inputs`, and carries a limitation that this does not prove absence of vulnerabilities. JavaScript coverage: `validateReviewFindingDraftSetSemantics`, `normalizeCandidateFindings`, and worker no-findings tests.

These invariants carry `not_applicable_review_finding_normalization_is_server_side` as their Rust marker: Review Finding Draft normalization is a vendor-side worker concern that consumes Local Runner scanner artifacts after receipt. The Local Runner remains responsible only for producing Candidate Findings and pre-submission artifacts.

## Reviewer classification invariants (Story 3.2)

Story 3.2 introduces `finding-classification-record.schema.json` as the protocol-owned artifact for expert reviewer judgment. It consumes Story 3.1 Review Finding drafts and deliberately keeps classification separate from scanner output, customer remediation status, accepted-risk records, false-positive records, validation scripts, and Attestation copy:

- **Allowed taxonomy** (`finding-classification-allowed-taxonomy`) — classification records may only use `likely`, `confirmed`, `inconclusive`, or `requires_customer_side_validation`. Scanner, remediation, validation, accepted-risk, false-positive, and Attestation states are not classification values. JavaScript coverage: `validateFindingClassificationRecordSemantics`, `finding-classification-record.disallowed-classification.json`, protocol-ts taxonomy tests, and finding-classification convergence tests.
- **Reviewer-only actor authority** (`finding-classification-reviewer-only-actor-authority`) — classification records and `classification_recorded` events may only be authored by CodeAttest reviewer actors. Customer workflow, remediation, accepted-risk, validation, and other non-reviewer events cannot create or rewrite expert classification history. JavaScript coverage: `validateFindingClassificationRecordSemantics`, `validateReviewEventSemantics`, `buildFindingClassificationEvent`, `appendReviewEvent`, the customer-authored classification and customer-classification-actor fixtures, and both classification/review-event convergence tests.
- **Confirmed guardrails** (`finding-classification-confirmed-guardrails`) — `confirmed` requires explicit confirmation criteria and rationale; if the evidence basis is only scanner, metadata, unavailable, not-submitted, never-collected, or unresolved evidence, `defensible_confirmation_criteria` must explain why the threshold is crossed. JavaScript coverage: `validateFindingClassificationRecordSemantics`, protocol-ts schema tests, classification negative fixtures, and control-plane guardrail tests.
- **Validation path required** (`finding-classification-validation-path-required`) — `requires_customer_side_validation` must carry a validation path summary or reference so the record cannot become an empty validation-required label. JavaScript coverage: `validateFindingClassificationRecordSemantics`, `buildFindingClassificationEvent`, `finding-classification-record.validation-required-without-path.json`, protocol-ts validation-path cases, and finding-classification convergence tests.
- **Append-only classification history** (`classification-events-append-only-history`) — classification updates are appended as `classification_recorded` events referencing typed classification artifacts. Updates use `supersedes_event_id` or prior classification record references, previous classification history remains visible, and callers still append through `appendReviewEvent`. JavaScript coverage: `buildFindingClassificationEvent`, `appendReviewEvent`, `validateReviewEventLogSemantics`, and `finding-classification.test.mjs` update/idempotency cases.
- **Classification text source safety** (`finding-classification-text-source-safety`) — classification rationale, criteria, threshold gaps, limitations, and validation-path text must not carry raw source bytes, raw scanner stdout/stderr, secrets, token-like strings, or claim-unsafe assurance copy. JavaScript coverage: `validateFindingClassificationRecordSemantics`, `finding-classification-record.raw-source-in-rationale.json`, `finding-classification-record.claim-unsafe-validation-path-ref.json`, finding-classification convergence tests, and control-plane forbidden-text cases.

These invariants carry `not_applicable_finding_classification_is_server_side` as their Rust marker: expert classification is a server-side reviewer/control-plane concern. The Local Runner produces scanner inputs and pre-submission evidence artifacts only; it never produces expert classifications.

## Remediation guidance and customer status invariants (Story 3.3)

Story 3.3 adds three protocol-owned retained review artifacts while preserving the Story 3.1/3.2 separation between scanner inputs, expert judgment, customer workflow metadata, and later verification outcomes:

- **Guidance status matrix** (`remediation-guidance-status-matrix`) — reviewer guidance uses the bounded statuses `actionable_guidance_provided`, `limited_guidance_requires_validation`, and `guidance_unavailable_from_submitted_evidence`. Actionable guidance is only valid for actionable classification context and requires meaningful remediation steps, validation steps, limitations, evidence references bound to available draft evidence, and exploitability rationale for likely/confirmed classifications. Limited or unavailable guidance requires a specific insufficient-evidence reason plus a next step or validation-path handoff. JavaScript coverage: `validateFindingRemediationGuidanceSemantics`, `finding-remediation-guidance.likely-actionable.json`, `finding-remediation-guidance.requires-validation-path-only.json`, `finding-remediation-guidance.evidence-ref-unbound.json`, `remediation-guidance-protocol.test.mjs`, `remediation-guidance.test.mjs`, and `remediation-guidance-convergence.test.mjs`.
- **Guidance text source and claim safety** (`remediation-guidance-text-source-safety`) — reviewer guidance text, limitations, validation summaries, and optional validation references are checked against the shared source-text and claim-safe phrase lists so guidance cannot embed raw source, scanner stdout/stderr, secrets, token-like strings, unqualified assurance copy, or absence-of-vulnerabilities claims. JavaScript coverage: `validateFindingRemediationGuidanceSemantics`, `finding-remediation-guidance.raw-source-text.json`, `finding-remediation-guidance.claim-unsafe-copy.json`, `claim-safety.test.mjs`, and remediation guidance convergence tests.
- **Customer status stays customer metadata** (`customer-remediation-status-no-rewrite`) — customer remediation status records may capture owner, status, due date, target state, notes, and explicit field export posture, but must not rewrite expert classification or reviewer remediation rationale. The bounded status vocabulary excludes accepted-risk and false-positive states; those remain Story 3.5 artifacts. JavaScript coverage: `validateCustomerRemediationStatusRecordSemantics`, customer status fixtures, `remediation-guidance.test.mjs`, and `remediation-guidance-convergence.test.mjs`.
- **Customer-facing finding state stays separated** (`customer-facing-finding-state-separation`) — customer-facing finding records distinguish expert classification, evidence basis/limitations, reviewer remediation guidance, customer remediation status metadata, verification state, and later accepted-risk/false-positive visibility. A single ambiguous status field is invalid, actionable customer-facing evidence requires at least one evidence ref, `latest_status_record_ref` must be listed in `customer_status_record_refs`, `remediated_by_customer` is not verification, and hidden customer notes are not exported as customer-facing/evidence-consumer copy. JavaScript coverage: `validateCustomerFacingFindingRecordSemantics`, `customer-facing-finding-record.actionable-empty-evidence-refs.json`, `customer-facing-finding-record.latest-status-ref-missing.json`, `customer-facing-finding-record.verification-ref-mismatch.json`, `remediation-guidance.test.mjs`, and `customer-finding-record.test.mjs`.
- **Remediation events remain append-only expert/customer boundaries** (`remediation-events-append-only-boundary`) — reviewer guidance is recorded as a `remediation_guidance_recorded` event referencing a typed guidance artifact, while customer status uses the existing `customer_remediation_recorded` event type referencing a typed customer status artifact. Customer-authored events cannot supersede `classification_recorded` or `remediation_guidance_recorded` chains, including multi-hop supersedes chains, and typed event refs stay exact when callers bypass builders. JavaScript coverage: `validateReviewEventSemantics`, `validateReviewEventLogSemantics`, `appendReviewEvent`, `review-event-log.customer-supersedes-remediation-guidance.json`, `review-event-log.customer-supersedes-classification-through-guidance.json`, `review-event-log.customer-facing-reason-raw-source.json`, `review-event-log.customer-facing-reason-claim-unsafe.json`, and `review-event-convergence.test.mjs`.

These invariants carry `not_applicable_remediation_guidance_is_server_side` as their Rust marker: reviewer guidance, customer status capture, and customer-facing finding projections are server-side reviewer/customer workflow concerns. The Local Runner never creates remediation guidance, customer status updates, accepted-risk/false-positive records, verification decisions, or Attestation copy.

## Validation path and reviewer script invariants (Story 3.4)

Story 3.4 formalizes the validation handoff that Stories 3.2 and 3.3 intentionally kept lightweight:

- **Validation path branches stay distinct** (`validation-path-branch-contracts`) — a validation path is one of `remote_dynamic_testing`, `customer_run_script`, or `manual_steps`. Remote testing requires target, authorization assumption, method, safety constraints, and evidence artifacts to collect. Customer-run script paths require explicit reviewer validation script refs. Manual steps remain separate from scripts. JavaScript coverage: `validateFindingValidationPathSemantics`, validation-path fixtures, `validation-path-protocol.test.mjs`, and `validation-path.test.mjs`.
- **Reviewer validation scripts respect the included cap** (`reviewer-validation-script-included-cap`) — reviewer-authored scripts are either `included_base_package` with slot 1..3 or `additional_script_candidate_pricing_tbd` with no slot and explicit pricing-TBD copy. The control-plane builder receives prior included-script context so the fourth included script is rejected rather than silently bundled. JavaScript coverage: `validateReviewerValidationScriptSemantics`, reviewer-validation-script fixtures, and `validation-path.test.mjs`.
- **Validation artifacts remain append-only expert records** (`validation-events-append-only-boundary`) — validation path and reviewer script artifacts are recorded through `validation_recorded` review events with exact singleton artifact refs and reviewer actor authority. Customer-authored events cannot supersede validation path/script chains. JavaScript coverage: `appendReviewEvent`, `validateReviewEventSemantics`, `validateReviewEventLogSemantics`, and validation path control-plane tests.
- **Validation path/script copy is source-safe and claim-safe** (`validation-path-script-text-source-safety`) — validation path and script free text, command/script content, and projected customer-facing copy use the shared normalized source/claim-safety matcher and cannot imply verification complete, SOC 2 acceptance, certification, regulator approval, independent assurance, or absence-of-vulnerabilities claims. JavaScript coverage: `validateFindingValidationPathSemantics`, `validateReviewerValidationScriptSemantics`, invalid source/claim fixtures, `claim-safety.test.mjs`, and UI view tests.

These invariants carry `not_applicable_validation_paths_are_server_side` as their Rust marker: validation path and reviewer script authoring are server-side reviewer/control-plane concerns. The Local Runner may later run customer-side scripts or attach outputs through Epic 4 evidence intake, but it does not author expert validation path/script artifacts.

## False-positive and accepted-risk outcome invariants (Story 3.5)

Story 3.5 adds protocol-owned outcome artifacts that qualify downstream posture without rewriting reviewer classification, customer remediation status, validation paths, or future verification decisions:

- **Outcome records stay separate from classification/status** (`outcome-records-separate-from-classification-status`) — false-positive records and accepted-risk records are retained review artifacts. The reviewer classification taxonomy remains only `likely`, `confirmed`, `inconclusive`, and `requires_customer_side_validation`; customer remediation status remains workflow metadata and does not gain accepted-risk or false-positive states. JavaScript coverage: `validateFalsePositiveRecordSemantics`, `validateAcceptedRiskRecordSemantics`, `finding-classification-record.disallowed-classification.json`, `customer-remediation-status-record` taxonomy tests, and `outcome-record-protocol.test.mjs`.
- **False-positive records preserve finding visibility** (`false-positive-outcome-visible-with-rationale`) — false-positive records require reviewer actor authority, rationale, evidence basis bound to the normalized Review Finding draft evidence refs, limitations, timestamp, and classification/finding refs. `false_positive_recorded` events use exact singleton artifact refs and reviewer actors, and customer-facing projections include a record-backed false-positive section instead of dropping the finding. JavaScript coverage: `validateFalsePositiveRecordSemantics`, `buildFalsePositiveEvent`, `appendReviewEvent`, `projectCustomerFacingFindingRecord`, false-positive fixtures, outcome convergence tests, UI tests, and static-bundle projection tests.
- **Accepted risk requires customer-backed acceptance and stays claim-safe** (`accepted-risk-customer-backed-no-verification-claim`) — accepted-risk records require customer rationale or sign-off evidence; customer actor identity is retained as metadata when available but is not a substitute acceptance signal. The record may coexist with remediation and validation history but cannot rewrite classification, remediation, or verification state, and exported copy must not imply remediation, verification, auditor acceptance, control satisfaction, certification, regulator approval, independent assurance, or absence of vulnerabilities. JavaScript coverage: `validateAcceptedRiskRecordSemantics`, `buildCustomerAcceptedRiskEvent`, `appendReviewEvent`, accepted-risk fixtures, outcome convergence tests, UI tests, and static-bundle projection tests.

These invariants carry `not_applicable_outcomes_are_server_side` as their Rust marker: false-positive and accepted-risk authoring are server-side reviewer/customer workflow concerns. The Local Runner never authors these expert/customer outcome artifacts.

## Verification pass scope invariants (Story 4.1)

Story 4.1 starts Epic 4 by recording customer-selected verification-pass scope without deciding whether remediation succeeded:

- **Customer-backed selection** (`verification-scope-customer-backed-selection`) — `verification-pass-scope.schema.json` records selected Review Finding drafts for the included pass. Customer users may record selection directly; reviewer/vendor/service actors must carry `customer_actor_ref` or `customer_selection_evidence_ref`, and `local_runner` or scanner/worker actors cannot author selection. JavaScript coverage: `validateVerificationPassScopeSemantics`, `buildVerificationPassScopeEvent`, and `verification-pass-scope.no-customer-backed-selection.json`.
- **Selected-finding binding** (`verification-scope-selected-finding-binding`) — each selected finding preserves the Review Finding draft, classification record, current classification, remediation/customer status refs when supplied, formal validation path/script refs when supplied, and accepted-risk/false-positive refs when supplied. Selection never rewrites classification, remediation, validation, or outcome artifacts. JavaScript coverage: `validateVerificationPassScopeFixtureReferenceSemantics`, `projectVerificationPassScope`, and `verification-pass-scope.classification-binding-mismatch.json`.
- **Included window and script cap** (`verification-scope-included-window-and-script-cap`) — `pass_deadline` is no later than 30 calendar days after the recorded included-pass start timestamp, included Validation Script slots are unique 1..3, and additional script candidates remain separate with pricing TBD posture. JavaScript coverage: `validateVerificationPassScopeSemantics`, `verification-pass-scope.three-included-scripts.json`, and deadline/script-cap negative fixtures.
- **Selection is not a verification decision** (`verification-scope-selection-not-decision`) — Story 4.1 artifacts cannot carry follow-up commits, uploaded validation evidence, before/after outcomes, `verified_with_evidence`, `verification_complete`, fixed/remediated/resolved labels, Attestation/addendum content, fresh full-review copy, certification/control/auditor/regulator claims, or absence-of-vulnerabilities copy. JavaScript coverage: `validateVerificationPassScopeSemantics`, `verification-pass-scope.future-evidence-field.json`, and `verification-pass-scope.claim-unsafe-copy.json`.
- **Verification-scope events are append-only** (`verification-scope-events-append-only-boundary`) — scope records append `verification_scope_recorded` events with exact singleton `artifact_ref:<verification_pass_id-without-prefix>` refs and idempotency keys derived from `verification_scope:<review_id>:<verification_pass_id>:scope_version:<positive-integer>`. Exact replays remain no-ops; corrections use a higher scope version and may supersede only a prior verification-scope event for the same review/pass. They never supersede classification, remediation, validation, false-positive, accepted-risk, or future verification-decision chains. JavaScript coverage: `validateReviewEventSemantics`, `validateReviewEventLogSemantics`, `appendReviewEvent`, and `buildVerificationPassScopeEvent`.

These invariants carry `not_applicable_verification_scope_is_server_side` or `not_applicable_review_event_log_is_server_side` markers: verification-pass scope is a retained review artifact and control-plane append concern. Follow-up evidence intake, before/after verification decisions, and Attestation/addendum projection remain later Epic 4 stories.

## Attestation, static package, finalization, and pilot-learning invariants (Epic 5)

- **Attestation retained chain and claim safety** (`attestation-retained-chain-claim-safety`) — a versioned Attestation contains each required independently readable section exactly once, preserves selected scope/commit, method/tooling/disclosure, receipt chain, classifications, remediation/validation, verification, lifecycle/deletion, limitations, and retained supporting refs, and rejects source text or assurance/acceptance conclusions. Generation authority is reviewer or deterministic vendor service.
- **Approved optional mappings** (`supporting-evidence-approved-mapping-boundary`) — mappings are approved/versioned records in the bounded SOC 2 supporting-evidence, generic technology-risk, or customer-security-review vocabulary. They retain scope, method, receipt context, evidence refs, limitations, consumer decision authority, and a non-acceptance boundary; unapproved regional or framework conclusions are not protocol values.
- **Content-addressed minimized static projection** (`static-bundle-content-addressed-minimized-projection`) — `static_bundle_id` is stable across versions while each `static_bundle_manifest_id` identifies one canonical manifest version. Every included file has a digest/size/role/class, the Evidence Bundle is represented through canonical manifest/signature/identity and retained export-approved payload refs, and internal pilot learning cannot appear in files or included refs.
- **Offline portal independence** (`static-portal-offline-customer-safe-projection`) — fixed navigation, relative links, offline search, print/export, copy controls, and phone summaries are structural. Remote assets, analytics, live APIs, and runtime authorization dependencies are false by contract.
- **Customer finalization produces a new signed version** (`attestation-finalization-customer-new-version-boundary`) — only a customer actor finalizes/exports after visible limitations, receipt context, identity, and export consequences plus verified receipt/signature/deletion/portal prerequisites. The finalized manifest has a higher version and distinct identity; generated bytes are never mutated.
- **Internal pilot learning stays content-free** (`pilot-learning-internal-content-free-boundary`) — metrics and feedback are review-linked, bounded categorical/numeric metadata with caveats, `internal_only` visibility, and no PII or evidence content. Pilot events have no customer-facing free-text reason, and records are excluded from Attestation, bundle files, portal/search/print, and customer event projections.

All Epic 5 signing fixtures use `ml_dsa_65`, a surviving signing mode (`managed_key` or `enrolled_runner_key`), real ML-DSA-65 signature bytes, and explicit key-custody limitations. Nothing in these contracts selects hardware key custody, deployment, or consumer acceptance.
