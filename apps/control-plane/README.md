# Control Plane App

Home for the future Next.js control plane and vendor/customer web surfaces.

This app will eventually support vendor APIs, reviewer workbench surfaces, attestation workflows, and customer/evidence-consumer views. It depends on protocol contracts and shared UI packages.

## Story 2.5: evidence storage classification, access controls, and deletion events

`src/index.ts` exposes a pure, dependency-free boundary for CodeAttest's evidence-handling controls:

- `classifyStoredObject` — every stored object declares exactly one retention/source-derived class. `log_or_trace`, `analytics_record`, `crash_report`, and `support_attachment` objects may only be `never_collected` or `retained_review_artifact`, and `customer_opt_in_retained_source` is only permitted under `environment_profile: partner_pilot_real_snippet_ready`.
- `appendEvidenceLifecycleEvent` — append-only in memory: a new event's `sequence_number` must be strictly greater than every one present, `event_id` values are never reused, no prior event is altered, and replaying an identical body under an already-used `idempotency_key` is a no-op. An `evidence_deleted` event must reference a Deletion Evidence artifact; a status label alone is not a receipt of deletion.
- `recordOptInRetention` — customer opt-in retained source requires a bounded retention period, a customer approval reference, and the retained artifact identities, and is only recordable under the real-snippet-ready pilot profile.
- `enforceScopedAccess` — sensitive artifact inspection is tenant/review scoped for the MVP roles, default-deny: an unrecognized role is denied rather than allowed. An allowed inspection appends an `evidence_accessed` event carrying actor, timestamp, artifact reference, scope, and purpose where available; a denial appends nothing, so no event can imply an inspection that did not happen. Replaying an identical in-scope inspection is idempotent and stays `allowed`, returning the log unchanged.
- `buildEvidenceMinimizationProjection` — the six minimization categories stay visibly distinct, each pinned to exactly one source-derived class; one artifact may not appear under two different categories; and every `deleted_transient` entry must resolve to a supplied Deletion Evidence artifact rather than a dangling reference.

All five entry points validate their inputs at runtime and return a stable reason code rather than throwing, and every artifact they hand back is a deep copy, so a caller cannot reach back through a nested `actor`, `access_scope`, or `retention_period` object to alter something that already passed validation.

### Scope and deferred boundary

This is a protocol-first, synthetic-only slice. The boundary is pure by construction — it has no filesystem, network, process, database, object-store, queue, or Cloud SDK reach.

`test/evidence-storage.test.mjs` enforces that with a static source scan, and it is worth being precise about the scan's scope so the guarantee is not read wider than it is: it reads every `.ts` file under `apps/control-plane/src/` and fails if any matches an import specifier for a Node core module (with or without the `node:` prefix, including subpaths), a `require(...)` or dynamic `import(...)` of one, a bare `fetch(`, or a database/queue/cloud client package. The core-module list includes `node:module`, since `createRequire` would otherwise re-open every specifier the scan blocks. It is a textual scan of `apps/control-plane/src/` only: it does not sandbox the runtime, it does not analyze dependencies, and — worth naming explicitly — it does not follow the deep relative import into `packages/protocol-ts/src/`, which is first-party code compiled into the same output rather than a transitive dependency, so a Node core import added there would not be caught here. All fixtures are synthetic and carry `SYNTHETIC_DEMO_DATA` / `NOT_CUSTOMER_SOURCE` markers where the closed schemas permit free text.

Explicitly **not** implemented here, and deferred to pilot hardening (Story 2.7 / pilot) behind the raised evidence-handling gates that `environment-evidence-gate` (Story 2.0) already governs:

- at-rest cryptographic encryption, KMS or Secret Manager key custody;
- real cloud IAM or access-control middleware, authentication, and session handling;
- any live datastore, object store, queue, or worker that actually holds evidence;
- acceptance of real (non-synthetic) customer Raw Snippets — the environment evidence gate remains the only thing that unblocks that, and nothing in this slice changes its semantics.

Story 2.5 identities are stable pattern-validated strings, not content-addressed hashes: this is deliberately *not* Story 2.4's hash-chained review event log, and nothing here is persisted or projected into a transparency log.

Story 2.6 adds `buildSubmissionOutcomeEvent`, which turns a failed `submission-outcome` into a `submission_rejected` / `submission_quarantined` event for the existing Story 2.4 `review-event-log`, and `projectSubmissionFailureNotice`, which emits a claim-safe customer notice (or `null` for `received_with_receipt`, because a success is never a blocking warning). Callers still append with `appendReviewEvent`; this boundary adds no second history artifact or append path. The outcome record itself is produced in `services/intake`, where the disposition is decided and the receipt is minted.

Story 3.2 adds `buildFindingClassificationEvent`, which turns a typed `finding-classification-record` artifact into a compact `classification_recorded` event for the same append-only `review-event-log`. The classification record owns expert-review semantics: allowed taxonomy, draft evidence-ref binding, evidence basis, confirmation criteria, threshold gaps, limitations, validation-path summary/reference, reviewer actor, and visibility. The event only references that artifact, derives idempotency from `(review_id, classification_record_id)`, and optionally carries `supersedes_event_id` for updates. Callers still append through `appendReviewEvent`; this boundary does not add a second classification history, does not mutate prior events, and does not write storage directly. `appendReviewEvent` also rejects forged `classification_recorded` events unless the actor is a reviewer, and rejects customer-authored events of any event type from superseding expert classification history. Later customer workflow states must reference or build on classification without rewriting it.

Story 3.3 adds `buildFindingRemediationGuidanceEvent`, `buildCustomerRemediationStatusEvent`, and `projectCustomerFacingFindingRecord`. Reviewer-authored `finding-remediation-guidance` artifacts become compact `remediation_guidance_recorded` events; customer-authored `customer-remediation-status-record` artifacts use the existing `customer_remediation_recorded` event type. Both builders validate typed artifacts, derive idempotency from their protocol identities, and still rely on `appendReviewEvent` for ordering and replay/conflict handling. Customer status events cannot supersede expert classification or reviewer remediation guidance chains, including multi-hop supersedes chains. The projection helper builds a `customer-facing-finding-record` read model that keeps expert classification, evidence basis/limitations, reviewer guidance, customer owner/status metadata, verification state, and future accepted-risk/false-positive visibility separate without mutating source artifacts or treating customer remediation as verification.

Story 3.4 adds `buildFindingValidationPathEvent` and `buildReviewerValidationScriptEvent`. Both use the existing `validation_recorded` review-event type and exact singleton artifact refs, derive idempotency from `validation_path_id` or `validation_script_id`, require reviewer actors, and still append only through `appendReviewEvent`. `appendReviewEvent` now treats reviewer-authored validation path/script chains as expert records that customer-authored events cannot supersede. The validation path builder binds paths to the classification/remediation context and keeps remote dynamic testing, customer-run scripts, and manual steps distinct. The script builder enforces included base-package slots 1..3 with prior included-script context; additional candidates preserve pricing-TBD posture and do not consume included slots. `projectCustomerFacingFindingRecord` can project customer-facing validation paths and reviewer scripts without marking verification complete; Epic 4 owns customer evidence intake and verification decisions.


Story 3.5 adds `buildFalsePositiveEvent` and `buildCustomerAcceptedRiskEvent`. False-positive records use the new `false_positive_recorded` review-event type, exact singleton `artifact_ref:<false_positive_id>`, reviewer actor authority, and idempotency derived from `(review_id, false_positive_record_id)`. Accepted-risk records use the existing `customer_accepted_risk_recorded` event type, exact singleton `artifact_ref:<accepted_risk_id>`, idempotency derived from `(review_id, accepted_risk_record_id)`, and customer-backed rationale/sign-off requirements even when a reviewer/vendor records the artifact. `appendReviewEvent` gates these by event type and typed artifact family rather than idempotency-key shape alone, blocks customer events from superseding expert false-positive chains, and allows corrections only within the same outcome family. `projectCustomerFacingFindingRecord` can now consume actual accepted-risk and false-positive records, validates their refs/visibility/export posture, projects record-backed outcome sections, and preserves verification state as `not_verified`/pending until Epic 4 artifacts exist.

Story 4.1 adds `buildVerificationPassScopeEvent` and `projectVerificationPassScope`. Verification scope records are retained review artifacts that record customer-selected findings for the included pass, not follow-up evidence or verification outcomes. The builder validates actor authority and customer-backed provenance, exact selected-finding refs, direct normalized-draft/classification/remediation/customer-status/validation/outcome binding, pass deadline semantics, formal validation-path eligibility for `requires_customer_side_validation`, included script slots 1..3, additional-script pricing-TBD posture, and claim-safe limitations. Events use `verification_scope_recorded`, exact singleton `artifact_ref:<verification_pass_id-without-prefix>`, and `verification_scope:<review_id>:<verification_pass_id>:scope_version:<positive-integer>` idempotency. Exact replay remains a no-op; a correction must use a higher scope version and supersede only a prior verification-scope event for the same review/pass. Direct append backstops reject local-runner/scanner-style authors, wrong refs, and cross-family supersedes; customer-authored scope events remain unable to supersede classification/remediation/validation/outcome chains. `projectVerificationPassScope` is a pure fail-closed customer-facing read model.

Stories 4.2 and 4.3 add pure metadata-only verification evidence and reviewer decision boundaries. `buildVerificationEvidenceIntakeRecord`, `buildVerificationEvidenceEvent`, and `projectVerificationEvidenceIntake` bind customer/customer-backed evidence metadata to the active eligible scope, original selected commit or formal validation path/script, access scope, lifecycle class, and concrete non-final intake state without storing payload bytes or inferring Git ancestry. `buildVerificationDecision`, `buildVerificationDecisionEvent`, and `projectVerificationDecision` require a reviewer actor, exact original classification/evidence/criteria basis, bound evidence records, canonical Epic 4 outcomes, limitations, and a next step for incomplete states. Both event families use exact singleton artifact refs, versioned derived idempotency, exact replay no-ops, active-head same-family correction, and the existing `appendReviewEvent` path.

Story 4.4 adds `projectVerificationAddendum`, a pure standalone addendum projection over the original review scope, selected commit, active verification scope, reviewer decisions, evidence records, deletion evidence, and same-review history events. Complete projection fails closed when retained artifacts, deletion evidence, or event links cannot be resolved; transient evidence is represented only through deletion evidence. `projectCustomerFacingFindingRecord` can now consume an actual customer-facing `verification_record` and emit its canonical reviewer outcome while retaining bare-ref compatibility as pending. These boundaries do not add hosted upload/API routes, persistence, external Git/object-store access, signing, Attestation generation, or production evidence acceptance.

## Epic 5 protocol-backed completion

Stories 5.1, 5.2, 5.5, and 5.6 add pure boundaries for `security-review-attestation`, approved supporting-evidence mapping, customer-owned package finalization/export, and internal-only pilot learning. Attestation generation resolves retained scope, bundle, receipt, lifecycle/deletion, verification-addendum, and append-only history references; mappings preserve evidence-consumer decision authority; finalization requires a customer actor and a newly signed higher manifest version; pilot records remain content-free, PII-free where applicable, and absent from customer history. Generated/finalized/exported/internal-learning events use the canonical `review-event` schema, derived versioned idempotency, exact singleton artifact refs, and metadata-only reasons. No live storage, external signer, hosted API, or production evidence gate is introduced.
